### Q11 — Connections graph: three-layer edge model from the derived index, rendered with sigma.js v3 + graphology <a id="warren-graph-rendering"></a>

**Decision:** The connections graph is a **view over the Q10 derived index**, never a direct vault reader. The index materializes nodes from typed frontmatter (npc/location/organization/artifact/pc/front/event — ~525 of the vault's 820 files today, with campaign/era/status/disposition/visibility as filter attributes) and edges from **three layers of decreasing structure** with a `kind` discriminator: (1) Relationship-Ledger notes (`type: relationship` frontmatter — richest: kind, current state, reciprocity, per-side knowledge, `known_to_players`); (2) relationship tables/sections in entity files (159 labeled edges today, behind ≥4 table-header variants — the parser sniffs tolerant headers, and authoring should drift toward the Ledger); (3) raw wiki links (1,672 typed-endpoint edges) as unlabeled context, shadowed whenever a labeled edge covers the same pair. Rendering: **sigma.js v3 + graphology + `@react-sigma`** — WebGL scale headroom, ForceAtlas2 in a worker, and `nodeReducer`/`edgeReducer` implementing exactly Warren's two core interactions (attribute filters, click-to-focus neighborhood dimming). Verified by a twin spike on the real vault (525 nodes/1,838 edges): sigma laid out and rendered in 176 ms with ~7 ms filter refreshes and rendered NPC↔NPC relationship status on edges (the Q9 acceptance example); Cytoscape's built-in layout blocked the UI for seconds at the same size. Relationship labels show on zoom/hover/focus, not all at once. graphology doubles as the in-browser graph model for prep queries; the same index edge table is Wren's query tool. Full survey + spike: [docs/research/2026-07-29-warren-graph-rendering.md](research/2026-07-29-warren-graph-rendering.md). Wayfinder ticket: [wren#8](https://github.com/johnalexwelch/wren/issues/8).
**Alternatives considered:** Cytoscape.js (best-in-class edge-label stylesheet control and the Dendron/Foam precedent, but canvas rendering is "workable, not silky" at growth scale, `react-cytoscapejs` is stale, and quality layout needs the fcose plugin in a worker — kept as the **named fallback** if sigma's edge-label typography proves insufficient; the data model ports unchanged); React Flow (node-editor: no layout engine, DOM wall at 1.8k+ edges); G6 v5 (capable; second fallback; heavy bundle, docs friction); d3-force + custom canvas (maximal control, but hand-rolls labels/hit-testing/a11y sigma already has); vis-network (dated, janky physics); Cosmograph (CC-BY-NC license, wrong scale class); NLP entity extraction for edges (re-rejected per Q9 — frontmatter + links + tables gets ~80% with zero inference risk).
**Tradeoff accepted:** Edge labels are canvas-drawn with zoom culling (labels-on-zoom/hover is the accepted UX — 1,672 labels at once is unreadable anyway); the multi-format table parser is the fragile surface until authoring converges on the Ledger; sigma v3 is ESM-only and its v4 alpha implies churn ahead; and the graph inherits the index's rebuild/invalidation surface — in exchange for 60 fps at double today's vault, ~10-line declarative filters, MIT licensing (~80 KB), an Obsidian-familiar feel that beats Obsidian on semantics, and a renderer that stays a swappable leaf behind the index.

### Q10 — Warren's backend is a thin TypeScript Agent SDK server pointed at the wren checkout <a id="warren-backend-agent-sdk"></a>

**Decision:** Warren's backend is built **thin on the Claude Agent SDK (TypeScript)** — a small Node server whose agent loop points at the wren checkout via `cwd` + `settingSources: ["user", "project"]`, so Wren's persona (`CLAUDE.md`), all 34 `.claude/skills/`, and auto-memory load as-is with no porting. Streaming to the browser uses `includePartialMessages` relayed over WebSocket. The Q7 canon-approval requirement and the Q9 staleness check share one choke-point: a `PreToolUse` policy hook on `Write|Edit` scoped to vault paths (holds regardless of permission mode), surfaced in the UI via the `canUseTool` callback. Sessions persist/resume by stored session ID (`resume`/`forkSession`). The Q9 services (vault watcher, derived index, embeddings) are app services beside the agent loop in the same TS runtime; the index is exposed to Wren as an MCP/in-process tool so chat, editor, and graph read the same data. No product is forked: server shell seeded from Anthropic's official `claude-agent-sdk-demos` patterns, with `claude-agent-kit`'s SessionManager/typed-WS-events vendored as useful; archived `claude-code-webui` (permission dialogs) and `opcode` (checkpoints) kept as UX references. First spike must verify the one undocumented assumption: auto-memory loading under SDK `settingSources`. Full survey: [docs/research/2026-07-29-warren-backend-survey.md](research/2026-07-29-warren-backend-survey.md). Wayfinder ticket: [wren#7](https://github.com/johnalexwelch/wren/issues/7).
**Alternatives considered:** Wrapping Claude Code headless (`claude -p --output-format stream-json`) as a subprocess (same engine, but no `canUseTool` runtime callback — the approval gate Q7 requires would need MCP permission-prompt plumbing or coarse allowlists); Python Agent SDK (splits the runtime from the React front-end and lacks the TS-only lifecycle hooks like `SessionStart`/`SessionEnd`); forking `siteboon/claudecodeui` (~13k★, most complete product — but AGPL, multi-CLI bloat to strip, per-tool toggles instead of per-write approval, and Warren's editor/graph/approval panes would be excavated into foreign architecture); adopting `claude-agent-kit` wholesale as a dependency (young, single-maintainer — vendor instead).
**Tradeoff accepted:** Warren owns its whole UI shell (no free file-tree/git-panel/mobile that a claudecodeui fork would give today) and depends on Agent SDK API stability, in exchange for first-party maintenance of the engine, an approval gate that is actually a policy choke-point, MIT-clean seeds, one TS runtime for loop + watcher + index, and zero porting of wren's skills and memory.

### Q9 — Warren is Obsidian-optional: plain files canonical, derived index, working editor, semantic graph bar <a id="warren-obsidian-optional"></a>

**Decision:** Warren neither commits to permanent coexistence with Obsidian nor targets replacing it — it is **Obsidian-optional**. The vault stays plain markdown files on disk as the source of truth; Warren must tolerate any external editor and no Warren feature may require Obsidian to be installed or running. If Warren gets good enough that Obsidian falls out of daily use, that's a welcome outcome, not a v1 goal. Five bindings: (1) **Editor** — v1 ships a *working* editor (markdown + save, frontmatter as a form/badge strip, clickable `[[wiki links]]`), built on a component that can grow toward Obsidian-grade later (Alex expects to want a fuller editor eventually); templates/multi-pane/WYSIWYG/mobile are out. (2) **Concurrency** — vault watcher; clean buffers auto-refresh; dirty buffer + disk change raises a reload-theirs/keep-mine/diff banner; staleness check (mtime/hash) on every save; agent writes flow through the same path plus the canon-approval gate; no CRDTs/merges/locks. (3) **Derived index** — Warren ingests the vault into a local rebuildable index (SQLite-class: metadata, frontmatter, link graph, embeddings) for retrieval and the graph; files remain canonical, the index is a disposable cache. (4) **Graph bar** — campaign-semantic, not parity: typed nodes from frontmatter, filters (campaign/era/status/disposition/visibility), labeled edges from relationship tables and the Relationship Ledger; acceptance examples: NPC↔artifact/location connections, NPC↔NPC relationship *status* on the edge. (5) **Plugin rationale recorded** — a plugin runs inside Obsidian's runtime (the coupling this decision rejects), Wren's agent backend doesn't fit the plugin sandbox anyway, and the chat-first/approval-gated UX fights it. Wayfinder ticket: [wren#5](https://github.com/johnalexwelch/wren/issues/5) (full resolution comment). Unblocks wren#8.
**Alternatives considered:** Coexist permanently (the initial recommendation — reversed after Alex's pushback: "when Warren is dialed in, why would I go back? Obsidian is a little cumbersome anyway"; the permanent framing contradicted the real trajectory while buying nothing v1 doesn't already build); replace Obsidian outright (re-fights Obsidian's strongest front — editor polish, plugins, mobile — instead of building what only Warren can be, and makes Warren a single point of failure for game night); database as source of truth with files as export (loses git-ability, portability, Wren's file-based toolchain, and the safe fallback); read-only viewer with Wren-mediated writes only (infuriating for trivial fixes); full knowledge-graph with NLP entity extraction (research project; frontmatter + links + relationship tables gets ~80% with zero inference risk); auto-merge on conflict (silent merges corrupt canon).
**Tradeoff accepted:** Warren carries coexistence machinery (watcher, conflict banner, staleness checks) even if Obsidian usage eventually drops to zero; the v1 editor will feel spartan next to Obsidian for long-form writing; and the index adds a rebuild/invalidation surface — in exchange for a lean v1, a safe fallback editor at all times, and no lock-in to either tool.

### Q8 — The workbench is named Warren and lives in its own repo, on local Forgejo <a id="warren-code-home-and-name"></a>

**Decision:** The Wren Workbench app is named **Warren**, and its code lives in a **new dedicated repo on Alex's local Forgejo instance** (`awelch/warren`) rather than inside `wren` or on GitHub. The name hides *wren* inside a word for a network of connected passages — the vault's link graph the app exists to navigate. Hosting follows the pergamon cutover (tracker guidance is forgejo-primary): Warren is born on Forgejo, and its delivery-funnel issues/PRs live there via the Forgejo API/`tea` (not `gh`). `wren` stays a persona/skills/canon repo; Warren points at the `wren` checkout (persona `CLAUDE.md`, `.claude/skills/`, auto-memory) and the Obsidian vault by configured paths, so the coupling is path config, not code. Scope is Warren only: the wayfinder map and `wren` itself stay on GitHub until this effort completes — wren's migration belongs to pergamon's cutover backlog. The repo is not created until the funnel builds it (plan, don't do); scaffold/template choices are delivery decisions informed by the backend survey. Wayfinder ticket: [wren#6](https://github.com/johnalexwelch/wren/issues/6) (see amendment comment).
**Alternatives considered:** Inside `wren` as an `apps/` subdir (one repo and tracker, no path config — but node_modules, builds, and app CI change the repo's character, and PRD issue volume would drown the D&D/skill work); GitHub `johnalexwelch/warren` (the initial pick this session — reversed because pergamon's whole purpose is moving off GitHub, and a repo that doesn't exist yet migrates for free); also migrating the wren map to Forgejo now (rejected: mid-effort tracker migration friction, GitHub sub-issue relations don't port 1:1); other names — Wren Workbench (descriptive but flat), Bower, Scriptorium, Drafting Table, Roost, Perch.
**Tradeoff accepted:** Two repos on two forges during the transition (map + decisions on GitHub `wren`, code + delivery issues on Forgejo `warren`), agent tooling for Warren must use the Forgejo API/`tea` instead of the `gh`-based skill conventions, and availability depends on the local instance — in exchange for keeping `wren` a pure persona/canon repo, giving the app a real delivery home, and advancing the off-GitHub cutover instead of against it.

### Q7 — Wren Workbench chat is a work surface, not fleet chat; bridged to Matrix by session summary <a id="wren-workbench-chorus-fit"></a>

**Decision:** The Wren Workbench (local web app: chat with Wren, vault browse/edit, connections graph) is a hybrid. Its chat is a **work session surface** — the Claude Code pattern with a better face: transcripts are session artifacts; tool calls, file edits, and skill runs stream inline. This sits outside Chorus F9's "no custom chat" rule, which governs *fleet conversation*; that plane is untouched — quick conversational asks to Wren stay on Matrix (`@wren`, Element), and the workbench does not replace or proxy Matrix. The bridge: on session end, Wren posts a short summary (work done, files touched, decisions) to her Matrix room, and the workbench emits standard F13 audit events to `~/.chorus/audit`, preserving Mira's observability. Wren's charter constraint (canon writes require Alex approval) must surface as an approval step in the workbench UI. Wayfinder ticket: [wren#4](https://github.com/johnalexwelch/wren/issues/4).
**Alternatives considered:** Treat workbench chat as fleet conversation and build it as a Matrix client (F9-pure, but Element/Matrix can't render tool streams, diffs, or skill runs — the actual content of a work session); full transcript mirroring to Matrix (maximum fidelity, but noisy and duplicates the session artifact); audit events only with no Matrix trace (clean, but work sessions become invisible to the fleet conversation record).
**Tradeoff accepted:** A second conversational surface for Wren exists (workbench + Element), in exchange for a work surface that can actually render agent work; the summary-plus-audit bridge keeps the fleet record whole. The "work surfaces are not chat" interpretation should also be noted fleet-side in chorus's decision log so F9's boundary is written down.

### Q5 — CANON.md rejected; tiered context loading adopted for session prep

**Decision:** Skip CANON.md as a manually-maintained artifact. Root cause of AI re-litigating settled decisions is that `dnd-session-prep` never reads `Decision Log.md` or `Story So Far.md`. Fix the actual gap: add Decision Log (LOCKED entries, filtered by relevance), Story So Far, and Storylines & Fronts (active fronts only) as Tier 2 mandatory reads in session prep. No new file to maintain. CANON.md would have required a sixth manual post-session update, compressed 39.9K of Decision Log to 3-4K with lossy results, and become poisonous when stale.
**Alternatives considered:** CANON.md as always-read dense summary (Karpathy-style, ~3-4K words) — rejected: maintenance burden, compression loss on long campaigns, staleness worse than no summary; AI-generated CANON.md regenerated each session — plausible but adds latency and creates a derived artifact; RAG/embeddings — overkill for a single-GM creative domain at this scale.
**Tradeoff accepted:** Tier 2 reads can be heavier per session than a single CANON.md read, in exchange for no maintenance artifact, no staleness risk, and Decision Log remaining the single source of truth.

### Q5 — PLAYER_KNOWLEDGE.md gap closed with new dnd-player-knowledge-sync skill

**Decision:** `PLAYER_KNOWLEDGE.md` was listed in `dnd-session-prep` as a context source but didn't exist and had no creation mechanism. Add `dnd-player-knowledge-sync` skill: runs post-session (triggered from recap-loop Step 11), extracts player-visible information from the session note (NPCs met, facts learned, rumors heard, secrets revealed), appends to `PLAYER_KNOWLEDGE.md`. Append-only; never overwrites history. Session-prep reads it in Tier 2 to prevent clues from re-delivering already-known information or leaking unrevealed secrets.
**Alternatives considered:** Infer player knowledge from session notes during prep (fragile, slow, inconsistent); skip it entirely (perpetuates the GM-knowledge-leak risk).
**Tradeoff accepted:** One additional post-session pass, in exchange for a durable player/GM knowledge boundary that survives across prep sessions.

### Q1 — Two buckets for name reconciliation, split by "would this resolve silently, everywhere?"

**Decision:** Two mechanisms. (1) Strings you always want to resolve to an entity → Obsidian native `aliases:` frontmatter (spelling variants, typos, in-world short forms). (2) Context-dependent transcription garble that must NOT resolve globally (e.g. "silver"→Ciradyl, "half-orc"→Veylar) → a small ingestion-only garble list, consulted only during transcript ingestion.
**Alternatives considered:** Single central alias-map file (duplicates Obsidian's native behavior, rots out of sync); pure-native only with no garble list (loses the catches that actually corrupted canon).
**Tradeoff accepted:** Two mechanisms instead of one, in exchange for not polluting the global namespace with transcription noise and not rebuilding what Obsidian does natively.

### Q2 — Native aliases auto-resolve; garble list flags for confirmation; consumption wired into ingestion skills

**Decision:** Native `aliases:` resolve silently (safe by definition). The garble list is flag-for-confirmation during ingestion, never auto-substituted. Make the behavior durable in `dnd-session-recap-loop` and `dnd-lore-ingestion` rather than leaving it in a WREN memory note that no skill reads.
**Alternatives considered:** Auto-substitute garbles (launders transcription noise into canon); leave consumption in the memory note (keeps not firing).
**Tradeoff accepted:** A confirmation step during ingestion, in exchange for never silently fusing conflicting entities (see the Osborn/Oswald D'emon split).

### Q3 — Scope is error-correction (garbles + spelling variants); diegetic aliases kept separate

**Decision:** The reconciliation system covers transcription garbles and spelling/typo variants only. In-world epithets/titles ("the Uncrowned King," "the Sapphire City") remain legitimate `aliases:` entries but are treated as worldbuilding, not error-correction; the garble list stays error-only.
**Alternatives considered:** One unified alias concept (loses the "is this noise?" signal); fold epithets in now (muddies the test).
**Tradeoff accepted:** Two conceptual categories sharing one frontmatter field, in exchange for keeping the garble list's intent clear.
