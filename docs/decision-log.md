### Q16 — Chat memory stays thin: SDK sessions + auto-memory unchanged, no Warren memory layer <a id="warren-chat-memory"></a>

**Decision:** Warren adds **no memory system of its own**. Chat sessions persist and resume via the Agent SDK's stored session IDs (`resume`/`forkSession`, already in Q10), surfaced in the shell as a session list (title, campaign, last-active; resume or fork from it). Claude Code **auto-memory keeps working unchanged** — the agent loop runs with `cwd`+`settingSources` at the wren checkout, so Wren reads and writes `memory/` exactly as she does in a terminal session today (memory writes land in the wren repo and are therefore approval-gated per Q13). Durable knowledge stays where it already lives: **canon → the vault** through the approval gate; **session trace → the Q7 Matrix summary + F13 audit**; **working memory → auto-memory `memory/`**. Warren stores only the session-ID table and display metadata. The Q10 first-spike (verify auto-memory loads under SDK `settingSources`) is the load-bearing assumption for this decision — if it fails, that spike escalates back to this question. Wayfinder ticket: [wren#24](https://github.com/johnalexwelch/wren/issues/24).
**Alternatives considered:** A Warren-side memory layer (per-campaign summaries auto-written to the vault or `memory/` — rejected: a second memory system to keep coherent with auto-memory, plus a new unattended write surface that either bypasses or spams the approval gate); semantic search over past chat transcripts (the Q11 index + vault already hold the knowledge worth retrieving; transcripts are session artifacts, not canon); persisting transcripts into the vault (pollutes canon with conversation).
**Tradeoff accepted:** Cross-session recall is only as good as auto-memory + the vault + resuming the right session — there is no v1 semantic search over old chats — in exchange for one memory model shared with terminal Wren, zero new write surfaces (Q13's posture holds untouched), and no coherence problem between competing memories.

### Q14 — Warren delivery splits into three PRDs: vault index, agent backend, workbench shell <a id="warren-prd-split"></a>

**Decision:** Warren's delivery funnel runs as **three PRDs in one build order: (1) vault index → (2) agent backend → (3) workbench shell**, each routed through `/to-prd` → `/to-issues` → `/triage` on Forgejo `awelch/warren` (per Q8). **PRD 1 — Vault index**: the Q11 data layer as its own workstream because it is shared infrastructure and the fragile surface — typed-frontmatter node extraction, three-layer edge parsing (Relationship Ledger / tolerant relationship-table sniffing / wiki links with labeled-edge shadowing), alias resolution at index time, SQLite-class rebuildable store (metadata, link graph, embeddings), the vault watcher with incremental invalidation, and staleness metadata (mtime/hash) that Q9's save check reads; exposes one query API consumed by everything downstream; no UI; testable against the real vault (spike extractors exist). **PRD 2 — Agent backend**: the Q10 server — Agent SDK loop (`cwd`+`settingSources` at the wren checkout), session resume/fork, `includePartialMessages`→WebSocket streaming, the `PreToolUse`+`canUseTool` choke-point (canon approval + staleness gate, posture per Q13), F13 audit events + Matrix summary bridge (Q7), and the index mounted as Wren's tool; its first task is the auto-memory-under-`settingSources` spike (the one undocumented Q10 assumption). **PRD 3 — Workbench shell**: the Q12 three-pane studio — tree / rendered-markdown editor (edit-source toggle, frontmatter strip) / chat rail, relationship table under the editor, on-demand sigma.js graph overlay with Q11 filter chips, inline tool streams, canon-approval card, staleness banner. Two interfaces get pinned early because they are the cross-PRD contracts: the **index query API** (PRD 1 → 2 and 3) and the **WebSocket event protocol** (PRD 2 → 3); the shell may start against fixtures before the backend lands. Table mode stays out until its fog clears (map #3). Wayfinder ticket: [wren#19](https://github.com/johnalexwelch/wren/issues/19).
**Alternatives considered:** Two PRDs (backend absorbs the index — Q10 already puts them in one TS runtime; rejected: one oversized PRD hiding the highest-risk parsing work inside server plumbing, and the index's consumers are mostly *not* the agent loop); the map's original three (backend / shell+editor / graph — rejected: Q12 dissolved the graph seam by mounting the overlay and the rel-table inside the shell, leaving a graph PRD that is mostly a component); one monolithic PRD (no seams to confirm, but no independent triage/build order either).
**Tradeoff accepted:** Three funnel runs and two pinned contracts instead of one big drop — and the index/backend boundary must resist scope leak (the watcher lives with the index, not the server) — in exchange for the fragile parsing surface getting dedicated review, a backend PRD that starts with its riskiest assumption, and a shell PRD that can build against fixtures in parallel.

### Q13 — Warren security posture: localhost + per-launch token, deny-by-default agent scope, approval as the only write path <a id="warren-security-posture"></a>

**Decision:** Warren's security posture treats the vault as **untrusted input** (any note can carry a prompt injection) and Wren's output as untrusted until approved. Five commitments, all v1: (1) **Network** — hardcoded `127.0.0.1` bind, a per-launch random bearer token required on every HTTP request and WebSocket handshake (delivered once via URL fragment), a strict `Origin` allowlist on the WS upgrade (CSWSH — any open tab can otherwise connect to localhost WebSockets), and `Host` header validation against DNS rebinding; no accounts, no CORS. (2) **Agent scope** — `permissionMode: default` with the Q10 `PreToolUse` hook as authority: reads confined to vault + wren checkout + scratch; vault writes *and wren-repo writes* (persona/skills are a persistence vector) only via the Q7 approval card + Q9 staleness check; writes elsewhere denied with no approval path; Bash restricted to a path-checked read-only allowlist (`rg`, `grep`, `git log/diff/show`); `WebSearch` open, `WebFetch` behind a persisted domain allowlist with approval for new domains (the classic injection-exfil channel); `maxTurns` + per-session spend caps. (3) **Secrets** — API keys in `~/.config/warren/env` (0600), loaded server-side at startup, never in WS frames, the client bundle, or logs (redact auth-shaped values); Keychain is later hardening, not architecture. (4) **Audit** — F13 JSONL to `~/.chorus/audit`: session start/end, every tool call with policy decision, approvals/denials with content *hash* + size, fetch/search targets — **paths, hashes, decisions; never vault content, diffs, or chat text** (GM secrets stay out of the fleet-shared audit dir). (5) **Blast radius** — a vault-injected Wren can only propose diffs Alex sees, fetch allowlisted domains, and run read-only commands; residual risk is Alex approving a malicious diff, mitigated by rendering the real diff and git revertability. Full posture doc: [docs/research/2026-07-29-warren-security-posture.md](research/2026-07-29-warren-security-posture.md). Wayfinder ticket: [wren#15](https://github.com/johnalexwelch/wren/issues/15).
**Alternatives considered:** No auth on the UI because it's localhost-only (rejected: DNS rebinding and CSWSH mean "localhost" is reachable from any web page Alex has open, and the server writes canon and spends money); OS-level auth / login accounts (single-user machine — a per-launch token gates the same capabilities with zero account machinery); `acceptEdits` for lower-friction sessions (defeats the Q7 canon gate; the approval card *is* the product's trust model); unrestricted Bash so all 34 skills work unmodified (hands an injected note a shell; the read-only allowlist covers the actual skill usage patterns); free wren-repo writes since it's "just config" (CLAUDE.md and skills are Wren's instruction set — the highest-value injection persistence target); unrestricted WebFetch for research (open exfil channel for GM secrets via crafted URLs); Keychain-only secrets in v1 (better at-rest story but changes nothing architectural; env file ships now); logging full diffs to audit for richer observability (leaks campaign content into a fleet-shared directory).
**Tradeoff accepted:** Session startup carries token-URL friction, new research domains and every canon write interrupt for approval, some skills lose exotic Bash invocations, and audit events are deliberately less debuggable than full transcripts — in exchange for a posture where nothing Wren produces reaches disk, the network, or another process without a standing allowlist rule or Alex's explicit click, browser-side attacks on the localhost server are structurally closed, and the irreducible residual risk is narrowed to a human approving a visible diff that git can revert.

### Q12 — Warren layout: three-pane studio; connections as a relationship table with the full graph launched on demand <a id="warren-workbench-layout"></a>

**Decision:** Warren's workbench layout is a **three-pane studio**: vault tree (left rail), **rendered-markdown editor** (center, formatted view by default with an edit-source toggle and frontmatter as a properties strip), and **chat as a right-hand rail** — explicitly on the side so Alex can interact with files, connections, and graph while talking to Wren. The connections surface under the editor is a **relationship table**, not an always-on graph: one row per edge from the Q11 index (entity, relationship label, entity type, source layer), where clicking any entity anywhere — wiki link, table row, graph node — refocuses the whole workspace (note, tree selection, connections) on it. The Q9 staleness banner, Q7/Q10 inline tool streams, and the canon-approval card all slot into this shell as prototyped. Decided HITL over two rounds of toggleable static prototypes on fake vault data: round 1 compared chat-primary / three-pane-studio / graph-home shells; round 2 fixed the shell and compared focus-graph / typed-backlink-panel / relationship-table connection formats. Spike + answer capture: `docs/research/spikes/2026-07-29-workbench-layout/`. Wayfinder ticket: [wren#9](https://github.com/johnalexwelch/wren/issues/9). This was the last feeder for the workstream/PRD-split fog item.
**Alternatives considered:** Chat-primary with slide-over files/graph (buries the vault behind an overlay; wrong bet — Warren sessions are work *on* files, not chat with occasional file access); graph-as-home with docked chat (the graph is a navigation tool, not the home surface); always-on mini-graph strip under the editor (round 1's failure: "I can't dive into the visual" — too small to read, unclickable, wasted the slot); focus-graph as the connections format (divable but spatially noisy at strip height); typed-backlink panel (readable but flat — the table's relationship/type/source columns carry more per row).
**Tradeoff accepted:** The graph is one click away instead of ambient (accepted — the table answers "what connects here" faster than a thumbnail graph ever did), and the three-pane shell spends horizontal space (fine on a desktop workbench; mobile is out of scope per Q9) — in exchange for a layout where every pane is interactive during a chat session, connections are legible and clickable at rest, and the expensive renderer mounts only when invoked.
### Q11 — Connections graph: three-layer edge model from the derived index, rendered with sigma.js v3 + graphology <a id="warren-graph-rendering"></a>

**Decision:** The connections graph is a **view over the Q10 derived index**, never a direct vault reader. The index materializes nodes from typed frontmatter (npc/location/organization/artifact/pc/front/event — ~525 of the vault's 820 files today, with campaign/era/status/disposition/visibility as filter attributes) and edges from **three layers of decreasing structure** with a `kind` discriminator: (1) Relationship-Ledger notes (`type: relationship` frontmatter — richest: kind, current state, reciprocity, per-side knowledge, `known_to_players`); (2) relationship tables/sections in entity files (159 labeled edges today, behind ≥4 table-header variants — the parser sniffs tolerant headers, and authoring should drift toward the Ledger); (3) raw wiki links (1,672 typed-endpoint edges) as unlabeled context, shadowed whenever a labeled edge covers the same pair. Rendering: **sigma.js v3 + graphology + `@react-sigma`** — WebGL scale headroom, ForceAtlas2 in a worker, and `nodeReducer`/`edgeReducer` implementing exactly Warren's two core interactions (attribute filters, click-to-focus neighborhood dimming). Verified by a twin spike on the real vault (525 nodes/1,838 edges): sigma laid out and rendered in 176 ms with ~7 ms filter refreshes and rendered NPC↔NPC relationship status on edges (the Q9 acceptance example); Cytoscape's built-in layout blocked the UI for seconds at the same size. Relationship labels show on zoom/hover/focus, not all at once. graphology doubles as the in-browser graph model for prep queries; the same index edge table is Wren's query tool. Full survey + spike: [docs/research/2026-07-29-warren-graph-rendering.md](research/2026-07-29-warren-graph-rendering.md). Wayfinder ticket: [wren#8](https://github.com/johnalexwelch/wren/issues/8).
**Alternatives considered:** Cytoscape.js (best-in-class edge-label stylesheet control and the Dendron/Foam precedent, but canvas rendering is "workable, not silky" at growth scale, `react-cytoscapejs` is stale, and quality layout needs the fcose plugin in a worker — kept as the **named fallback** if sigma's edge-label typography proves insufficient; the data model ports unchanged); React Flow (node-editor: no layout engine, DOM wall at 1.8k+ edges); G6 v5 (capable; second fallback; heavy bundle, docs friction); d3-force + custom canvas (maximal control, but hand-rolls labels/hit-testing/a11y sigma already has); vis-network (dated, janky physics); Cosmograph (CC-BY-NC license, wrong scale class); NLP entity extraction for edges (re-rejected per Q9 — frontmatter + links + tables gets ~80% with zero inference risk).
**Tradeoff accepted:** Edge labels are canvas-drawn with zoom culling (labels-on-zoom/hover is the accepted UX — 1,672 labels at once is unreadable anyway); the multi-format table parser is the fragile surface until authoring converges on the Ledger; sigma v3 is ESM-only and its v4 alpha implies churn ahead; and the graph inherits the index's rebuild/invalidation surface — in exchange for 60 fps at double today's vault, ~10-line declarative filters, MIT licensing (~80 KB), an Obsidian-familiar feel that beats Obsidian on semantics, and a renderer that stays a swappable leaf behind the index.

### Q10 — Warren's backend is a thin TypeScript Agent SDK server pointed at the wren checkout <a id="warren-backend-agent-sdk"></a>

**Decision:** Warren's backend is built **thin on the Claude Agent SDK (TypeScript)** — a small Node server whose agent loop points at the wren checkout via `cwd` + `settingSources: ["user", "project"]`, so Wren's persona (`CLAUDE.md`), all 34 `.claude/skills/`, and auto-memory load as-is with no porting. Streaming to the browser uses `includePartialMessages` relayed over WebSocket. The Q7 canon-approval requirement and the Q9 staleness check share one choke-point: a `PreToolUse` policy hook on `Write|Edit` scoped to vault paths (holds regardless of permission mode), surfaced in the UI via the `canUseTool` callback. Sessions persist/resume by stored session ID (`resume`/`forkSession`). The Q9 services (vault watcher, derived index, embeddings) are app services beside the agent loop in the same TS runtime; the index is exposed to Wren as an MCP/in-process tool so chat, editor, and graph read the same data. No product is forked: server shell seeded from Anthropic's official `claude-agent-sdk-demos` patterns, with `claude-agent-kit`'s SessionManager/typed-WS-events vendored as useful; archived `claude-code-webui` (permission dialogs) and `opcode` (checkpoints) kept as UX references. First spike must verify the one undocumented assumption: auto-memory loading under SDK `settingSources`. Full survey: [docs/research/2026-07-29-warren-backend-survey.md](research/2026-07-29-warren-backend-survey.md). Wayfinder ticket: [wren#7](https://github.com/johnalexwelch/wren/issues/7).
**Alternatives considered:** Wrapping Claude Code headless (`claude -p --output-format stream-json`) as a subprocess (same engine, but no `canUseTool` runtime callback — the approval gate Q7 requires would need MCP permission-prompt plumbing or coarse allowlists); Python Agent SDK (splits the runtime from the React front-end and lacks the TS-only lifecycle hooks like `SessionStart`/`SessionEnd`); forking `siteboon/claudecodeui` (~13k★, most complete product — but AGPL, multi-CLI bloat to strip, per-tool toggles instead of per-write approval, and Warren's editor/graph/approval panes would be excavated into foreign architecture); adopting `claude-agent-kit` wholesale as a dependency (young, single-maintainer — vendor instead).
**Tradeoff accepted:** Warren owns its whole UI shell (no free file-tree/git-panel/mobile that a claudecodeui fork would give today) and depends on Agent SDK API stability, in exchange for first-party maintenance of the engine, an approval gate that is actually a policy choke-point, MIT-clean seeds, one TS runtime for loop + watcher + index, and zero porting of wren's skills and memory.

### Q9 — Warren is Obsidian-optional: plain files canonical, derived index, working editor, semantic graph bar <a id="warren-obsidian-optional"></a>

**Decision:** Warren neither commits to permanent coexistence with Obsidian nor targets replacing it — it is **Obsidian-optional**. The vault stays plain markdown files on disk as the source of truth; Warren must tolerate any external editor and no Warren feature may require Obsidian to be installed or running. If Warren gets good enough that Obsidian falls out of daily use, that's a welcome outcome, not a v1 goal. Five bindings: (1) **Editor** — v1 ships a *working* editor (markdown + save, frontmatter as a form/badge strip, clickable `[[wiki links]]`), built on a component that can grow toward Obsidian-grade later (Alex expects to want a fuller editor eventually); templates/multi-pane/WYSIWYG/mobile are out. (2) **Concurrency** — vault watcher; clean buffers auto-refresh; dirty buffer + disk change raises a reload-theirs/keep-mine/diff banner; staleness check (mtime/hash) on every save; agent writes flow through the same path plus the canon-approval gate; no CRDTs/merges/locks. (3) **Derived index** — Warren ingests the vault into a local rebuildable index (SQLite-class: metadata, frontmatter, link graph, embeddings) for retrieval and the graph; files remain canonical, the index is a disposable cache. (4) **Graph bar** — campaign-semantic, not parity: typed nodes from frontmatter, filters (campaign/era/status/disposition/visibility), labeled edges from relationship tables and the Relationship Ledger; acceptance examples: NPC↔artifact/location connections, NPC↔NPC relationship *status* on the edge. (5) **Plugin rationale recorded** — a plugin runs inside Obsidian's runtime (the coupling this decision rejects), Wren's agent backend doesn't fit the plugin sandbox anyway, and the chat-first/approval-gated UX fights it. Wayfinder ticket: [wren#5](https://github.com/johnalexwelch/wren/issues/5) (full resolution comment). Unblocks wren#8.
**Alternatives considered:** Coexist permanently (the initial recommendation — reversed after Alex's pushback: "when Warren is dialed in, why would I go back? Obsidian is a little cumbersome anyway"; the permanent framing contradicted the real trajectory while buying nothing v1 doesn't already build); replace Obsidian outright (re-fights Obsidian's strongest front — editor polish, plugins, mobile — instead of building what only Warren can be, and makes Warren a single point of failure for game night); database as source of truth with files as export (loses git-ability, portability, Wren's file-based toolchain, and the safe fallback); read-only viewer with Wren-mediated writes only (infuriating for trivial fixes); full knowledge-graph with NLP entity extraction (research project; frontmatter + links + relationship tables gets ~80% with zero inference risk); auto-merge on conflict (silent merges corrupt canon).
**Tradeoff accepted:** Warren carries coexistence machinery (watcher, conflict banner, staleness checks) even if Obsidian usage eventually drops to zero; the v1 editor will feel spartan next to Obsidian for long-form writing; and the index adds a rebuild/invalidation surface — in exchange for a lean v1, a safe fallback editor at all times, and no lock-in to either tool.

### Q5 — CANON.md rejected; tiered context loading adopted for session prep

**Decision:** Skip CANON.md as a manually-maintained artifact. Root cause of AI re-litigating settled decisions is that `dnd-session-prep` never reads `Decision Log.md` or `Story So Far.md`. Fix the actual gap: add Decision Log (LOCKED entries, filtered by relevance), Story So Far, and Storylines & Fronts (active fronts only) as Tier 2 mandatory reads in session prep. No new file to maintain. CANON.md would have required a sixth manual post-session update, compressed 39.9K of Decision Log to 3-4K with lossy results, and become poisonous when stale.
**Alternatives considered:** CANON.md as always-read dense summary (Karpathy-style, ~3-4K words) — rejected: maintenance burden, compression loss on long campaigns, staleness worse than no summary; AI-generated CANON.md regenerated each session — plausible but adds latency and creates a derived artifact; RAG/embeddings — overkill for a single-GM creative domain at this scale.
**Tradeoff accepted:** Tier 2 reads can be heavier per session than a single CANON.md read, in exchange for no maintenance artifact, no staleness risk, and Decision Log remaining the single source of truth.

### Q5 — PLAYER_KNOWLEDGE.md gap closed with new dnd-player-knowledge-sync skill

**Decision:** `PLAYER_KNOWLEDGE.md` was listed in `dnd-session-prep` as a context source but didn't exist and had no creation mechanism. Add `dnd-player-knowledge-sync` skill: runs post-session (triggered from recap-loop Step 11), extracts player-visible information from the session note (NPCs met, facts learned, rumors heard, secrets revealed), appends to `PLAYER_KNOWLEDGE.md`. ### Q1 — Two buckets for name reconciliation, split by "would this resolve silently, everywhere?"

**Decision:** Two mechanisms. (1) Strings you always want to resolve to an entity → Obsidian native `aliases:` frontmatter (spelling variants, typos, in-world short forms). (2) Context-dependent transcription garble that must NOT resolve globally (e.g. "silver"→Ciradyl, "half-orc"→Veylar) → a small ingestion-only garble list, consulted only during transcript ingestion.
**Alternatives considered:** Single central alias-map file (duplicates Obsidian's native behavior, rots out of sync); pure-native only with no garble list (loses the catches that actually corrupted canon).
**Tradeoff accepted:** Two mechanisms instead of one, in exchange for not polluting the global namespace with transcription noise and not rebuilding what Obsidian does natively.

### Q2 — Native aliases auto-resolve; garble list flags for confirmation; consumption wired into ingestion skills

**Decision:** Native `aliases:` resolve silently (safe by definition). The garble list is flag-for-confirmation during ingestion, never auto-substituted. Make the behavior durable in `dnd-session-recap-loop` and `dnd-lore-ingestion` rather than leaving it in a WREN memory note that no skill reads.
